# מעקב שינויים ושער-אימות לתכניות (תב"ע)

> מסמך זה מסכם את התקלה שהובילה לבניית המערכת, שורש הבעיה, והמנגנון בן שלושת השלבים
> שנבנה כדי שכל שינוי בנתוני תכנית יהיה **מתועד, גלוי, ומבוקר**.
> נכתב: 2026-08-02.

---

## 1. הרקע — התקלה שחשפה את הפער

בתכנית **101-1354356** (יוסי בן יועזר 12) הופיעה בפופאפ **הפרשה מבונה: "מגרש 2 - גן ילדים (130)"**.
בבדיקה מול המקורות הרשמיים התברר:

- **טבלה 5** של התכנית אינה כוללת גן ילדים כלל — ה-130 מ"ר שם הם **גודל מגרש המסחר** (שורה 2: מגורים ד'/שימוש מסחר, 130+15=145 מ"ר מסחר).
- **הוראות התכנית** (הטקסט המלא, ~32K תווים) אינן מזכירות ולו פעם אחת: גן ילדים / מעון / חינוך / שב"צ / מבנה ציבור / הפרשה / מסירה.

כלומר גן-הילדים **לא היה קיים** — הוא נכנס מקריאה ויזואלית שגויה של נספח הבינוי, שתייגה בטעות את מגרש המסחר (130 מ"ר) כגן ילדים.

**התיקון:** רוקנו את `hafrash_sqm` ו-`hafrash_prg` ב-GS המאסטר (שורה 668, עמודות AQ/AR) וב-`plans.geojson`
(commit `b7de31c`), וכן בקבצי ה-scratch של צינור הבינוי.

### הכלל שנקבע

> **הקצאת מבנה ציבור (גן ילדים, מעון, בי"ס, שב"צ) קיימת רק אם היא מופיעה בטבלה 5 או בהוראות/תקנון.**
> אם שני המקורות שקטים — אין מבנה ציבור, גם אם קריאת בינוי ויזואלית טוענת אחרת.

## 2. שורש הבעיה — למה זה חמק בלי שאף אחד ראה

מיפוי הצינור העלה חמישה פערים:

1. **אין שער-אימות על כתיבות אוטומטיות.** `hafrash_sqm`/`hafrash_prg` וערכי טבלה 5 נכתבים אוטומטית בכל שינוי סטטוס, ללא הצלבה מול הערך הקודם או מול ההוראות.
2. **מירור עיוור כל 10 דקות.** `scripts/update_plans.py` העתיק *כל* עמודות ה-GS ל-geojson ללא ולידציה — ערך שגוי עלה למפה הציבורית תוך ≤10 דקות.
3. **אין changelog מתמיד ברמת-שדה.** הדלתות old→new היו קיימות רגע אחד (במייל / progress JSON שנמחק בכל ריצה) ואז נעלמו. לא היה תיעוד פר-תכנית שאפשר לחזור אליו.
4. **הפרשה מבונה / קומות / סיווג `hafrash_prg` לא דווחו באף מייל.**
5. **הזיהוי מבוסס-מחרוזת-סטטוס בלבד** — הדריסות הכבדות רכבו כתופעת-לוואי של שינוי סטטוס, בלי הצלבה מול הישן.

**התובנה:** היסטוריית git של `plans.geojson` הראתה שגן-הילדים נכנס כבר בקליטה הראשונה של התכנית
ל-geojson (commit `c4f8062`, 12/07/2026), כחלק מכתיבה גורפת של כל השדות בבת-אחת — לא בשינוי מאוחר.

## 3. הפתרון — מערכת בת שלושה שלבים

```
Mavat ─(scrape)→ GS מאסטר ─(cron כל 10 דק')→ plans.geojson ─→ המפה החיה
                    │                    │
                    │            [שלב 1] changelog  ← כל שינוי-שדה נרשם לצמיתות
                    │            [שלב 3] שער-אימות   ← הקצאת ציבור חדשה נחסמת + לתור
                    │
              [שלב 2] מייל ← דיגסט שינויים רגישים + דגל 🚩
```

### שלב 1 — לוג שינויים מתמיד  (commit `864d43b`)

`scripts/update_plans.py`, בנקודת-החנק של המירור GS→geojson: בלולאת ההעתקה נלכד `old→new`
*לפני* הדריסה, ונרשם ל-**`data/plan_changelog.jsonl`** (שורה פר-שינוי-שדה).

- מבנה שורה: `{ts, taba, plan_name, status, field, old, new}` (ולפריט מוחזק: `"held": true`).
- `_norm()` מנטרל רעש-טיפוסים (`130`==`"130"`, `''`==`None`, `9.0`==`9`); מדלג על `last_modified`.
- כתיבה דרך GitHub Contents API; כישלון = non-fatal (לא שובר את המירור); cap 50000 שורות.

**כלי סקירה — `scripts/plan_history.py`:**
```bash
python scripts/plan_history.py <taba>       # היסטוריית שדות של תכנית
python scripts/plan_history.py --recent 40  # 40 השינויים האחרונים בכל התכניות
python scripts/plan_history.py <taba> --git # שחזור מהיסטוריית git (לפני קיום הלוג)
```

### שלב 2 — דיגסט במייל שינוי-הסטטוס  (commit `ade7bf2`)

`update_mavat_ui.py` (מקומי) מוסיף למייל סעיף **"🏛️ שינויי שדות רגישים"** הנבנה מ-`plan_changelog.jsonl`:

- `SENSITIVE_FIELDS`: הפרשה, שב"צ, יח"ד, מסחר, תעסוקה, קומות, גובה, חדר דיירים.
- **דגל אדום 🚩** על **הקצאת ציבור חדשה** (`_is_new_public_allocation`) עם הכיתוב *"לאמת מול טבלה 5/הוראות"*.
- Marker מקומי `C:\ORANIM\.last_changelog_email.txt` (לא בגיט) מונע דיווח כפול; ברירת-מחדל lookback 7 ימים.
- **תזמון:** שינויי המחזור הנוכחי נכתבים ע"י ה-cron *אחרי* המייל → מופיעים במייל הבא (lag של מחזור אחד).

### שלב 3 — שער-אימות  (commit `9618be1`)

`scripts/update_plans.py`, אותה נקודת-חנק. כשמזוהה **הקצאת ציבור חדשה** (אותו predicate של הדגל בשלב 2,
על `hafrash_prg`/`hafrash_sqm` = `GATED_FIELDS`):

- הערך **מוחזק** — לא נכתב ל-geojson החי (שאר השדות של אותה תכנית מתפרסמים כרגיל).
- הפריט נכנס ל-**`data/pending_review.json`** (מפתח `taba|field`, עם dedup).
- **fail-open:** אם התור לא נטען → השער מושבת לאותה ריצה (לעולם לא חוסם דאטה לגיטימית ולא שובר את המירור).

**כלי ניהול התור — `scripts/review_queue.py`:**
```bash
python scripts/review_queue.py                       # רשימת ממתינים לאימות
python scripts/review_queue.py approve <taba> [field] # מפרסם את הערך המוחזק ל-geojson החי
python scripts/review_queue.py reject  <taba> [field] --apply  # מנקה ב-GS המאסטר (לא יחזור)
```

## 4. זרימת עבודה מומלצת

1. מגיע מייל עם דגל 🚩 "הקצאת ציבור חדשה" לתכנית X.
2. הרץ `python scripts/review_queue.py` לראות את הפרטים.
3. בדוק את התכנית מול **טבלה 5** (`horaot/101-<taba>.pdf` — טקסט RTL הפוך, להריץ `line[::-1]`) ומול **ההוראות**.
4. אם מגובה → `approve <taba>` (מתפרסם למפה). אם לא → `reject <taba> --apply` (מנוקה מ-GS).

## 5. מגבלות ידועות

- השער חל רק על `hafrash_prg`/`hafrash_sqm` (מחלקת הכשל של 1354356), לא על שב"צ/שצ"פ.
- שינויי סטטוס שנכתבים ישירות ל-geojson ע"י `update_mavat_ui.update_geojson` עלולים לא להירשם ע"י ה-cron (הערך כבר עודכן → `old==new`).
- הלוג לוכד שינויים לפיצ׳רים *קיימים* ב-geojson; תכניות חדשות נקלטות ב-`detect_new_plans`, לא כאן.
- העבודה ברפו רגישה לריצות מקבילות + נעילות Google Drive — כתיבה תמיד: `git add` קבצים ספציפיים + commit מיד, ואז `git pull --rebase --autostash` + push.
